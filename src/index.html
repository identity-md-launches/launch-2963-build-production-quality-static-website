Guardrails for agents that pay.

The policy and observability layer for AI agent payments. Caps, allowlists and receipts, checked before an agent answers an x402 payment request.

Try the playground -> Read the docs

Agents can pay. Few can be told how much.

x402 lets an HTTP service answer with 402 Payment Required and lets a client pay per request. That is useful for agents, and it moves a spending decision into a loop that runs without a person watching.

Spend has no ceiling

A retry loop or a planning bug can repeat a paid call thousands of times. Without a cap, every repetition is a payment.

Spend is hard to see

Small per-request payments scatter across services. Operators need one record of what was paid, to whom, and why.

Spend can be steered

Agents read untrusted text. A page or tool result can try to change the payee, the price or the urgency of a request.

A policy layer between the agent and the wallet

PAY//AGENT proposes a small, deterministic component that sits in the agent's HTTP client. It decides whether a payment request may proceed, and it writes down every decision.

Deterministic rules

Plain configuration, evaluated in a fixed order. The model never decides whether to pay.

Receipts and logs

Each challenge, decision and result becomes a structured receipt you can query and export.

Human escalation

Payments above a threshold wait for a person. Below it, routine calls stay fast.

Instant revocation

Disable a policy, a payee or an agent key, and the next request is denied.

The request and payment lifecycle

Six stages. PAY//AGENT adds the third and records all of them. The other stages follow the public x402 pattern.

  1. Request

    The agent calls a paid HTTP endpoint the normal way, with no payment attached.

  2. 402 challenge

    The server answers 402 Payment Required with what it accepts: scheme, network, asset, amount, payee and a time limit.

  3. Policy check

    The proposed PAY//AGENT engine compares the challenge to the agent's policy: caps, rolling budget, allowlists, quote age and replay state.

  4. Authorization

    Only if every rule passes does the client ask its isolated signer for a payment authorization. Above a threshold, a human approves first.

  5. Retry

    The client repeats the request with the payment attached in a header, as the x402 specification describes.

  6. Result

    The server verifies and settles through its facilitator, returns the resource, and PAY//AGENT stores the receipt.

Where agents meet paid endpoints

Use cases the concept is designed around. None of these are deployments or customers.

Research agents

Buy single search results, filings or articles instead of holding a dozen subscriptions.

Coding agents

Pay per call for package audits, build minutes or documentation lookups during a task.

Data pipelines

Enrich records one request at a time, with a budget that stops the job when it is spent.

Model routing

Send a prompt to a paid inference endpoint only when the price fits the task's limit.

Compared with subscription APIs

Per-request payment is not always better. It fits agents that call many services occasionally.

QuestionSubscription API keyx402 with PAY//AGENT policy
OnboardingAccount, billing details and a key per providerNo account; pay on the first request
Cost shapeFixed monthly fee, often unusedPay per request; idle costs nothing
Spending limitSet per provider, if offeredOne policy across every provider
Credential leakKey works until rotatedBounded by caps, budget and allowlists
Audit trailSeparate invoices per providerOne receipt log per agent
Best forHeavy, predictable use of one serviceLight, varied use of many services
