Overview

PAY//AGENT is a proposed library that sits between an AI agent's HTTP client and its payment signer. When a server answers 402 Payment Required, the library checks the request against a policy file, then either authorizes the payment, denies it with a reason code, or holds it for a person.

Status: proposed. The package name @payagent/client below is a placeholder and is not published. Do not install anything under that name.

Quickstart

The intended setup has three steps: write a policy, wrap the agent's fetch, and pass a signer that never leaves its own process.

Until a release exists, the playground runs the same rule order in your browser with example data.

Proposed client and server flow

Client side (PAY//AGENT)

  1. Send the request unchanged.
  2. On a 402, parse the payment requirements from the response body.
  3. Drop requirements outside the network and asset allowlists. Pick the cheapest remaining one.
  4. Evaluate the policy and write the verdict to the ledger.
  5. On allow, ask the signer for a payment payload and retry with the x402 payment header.
  6. Record the response and any settlement header as a receipt.

Server side (unchanged x402)

PAY//AGENT does not require server changes. A server that follows the x402 specification returns a 402 challenge, verifies the retried payment, settles it through its facilitator, and returns the resource. Use the official x402 server middleware for this side.

Example HTTP 402 challenge

This follows the shape of the public x402 version 1 payment requirements. Field names can change between specification versions; check the official repository before relying on them.

Amounts are strings in the asset's base units. For a six-decimal stablecoin, "2000" means 0.002 units. Addresses are left as placeholders on purpose.

Policy configuration

A policy is one JSON file per agent. All amounts are decimal strings in whole units of the asset, converted to base units at load time.

KeyMeaning
activeSet to false to revoke. Every request is denied with PA_POLICY_INACTIVE.
networksAllowed network identifiers, as they appear in challenges.
assetsAllowed token contracts per network.
payeesallowlist pins payees per origin; any disables the check.
limitsPer-request cap, rolling budget and escalation threshold.
quotesMaximum age of a challenge before it must be refetched.
replayWhether and how long to remember used nonces.

Receipt format

One receipt per payment decision, including denials. Receipts are local records; they are not proof of settlement unless they include the server's settlement response.

Errors

Denials return a structured error to the agent, so it can explain the block instead of retrying. Codes are proposed.

CodeCauseWhat to do
PA_POLICY_INACTIVEPolicy or agent revokedRe-enable the policy if the revocation was a mistake
PA_NETWORK_NOT_ALLOWEDChallenge uses an unlisted networkAdd the network only if you monitor it
PA_ASSET_NOT_ALLOWEDChallenge uses an unlisted assetCheck the token contract with the service

Security guidance

  • Keep the signing key out of the agent's process, prompt and tools.
  • Fund the spending wallet with only what you can lose, and top it up deliberately.
  • Start on a testnet. Move to mainnet only after reviewing receipts for a while.
  • Pin payees for every service you pay. Treat a changed payee as an incident.
  • Store the policy where the agent cannot write to it.
  • Read the full security model before connecting real funds to anything.
